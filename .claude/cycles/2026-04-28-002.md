## CONTEXTO

- **Intenção de negócio observável:** Ao receber um webhook com `Idempotency-Key` já processada dentro da janela válida, o módulo `webhooks` deve rejeitar o reprocessamento e retornar o resultado anterior, evitando efeitos colaterais duplicados.
- **Módulo:** `webhooks`
- **Camada principal do teste:** unit + integration
- **Contratos afetados:** Comportamento observável do consumo de webhooks passa a considerar o header `Idempotency-Key` como insumo de controle de deduplicação.
- **Risco de segurança:** Médio; evita duplicidade operacional, mas exige cuidado para não reutilizar resposta entre tenants ou entre endpoints distintos.
- **Risco de tenant isolation:** Médio; a chave Redis deve incluir namespace por tenant/destino para impedir colisão cross-tenant.
- **Risco de performance:** Baixo; adiciona leitura/escrita leve em Redis por entrega.
- **Migration/schema afetado:** Nenhum, salvo se optar por trilha híbrida com persistência de deliveries.
- **Há legado sem cobertura?** Sim; o bootstrap já registrou ausência de idempotência em webhooks.
- **Estratégia de rollback:** `git revert <sha>`

## VERIFY

- **Comando executado:** `pnpm exec vitest run` no módulo `apps/api`.
- **Resultado da suíte global:** **74/74 testes passando** (1 skipped). Nenhuma regressão detectada nos módulos adjacentes ou testes existentes.
- **Checagem Tenant-aware:** A chave Redis (`webhook:idempotency:{tenantId}:{endpoint}:{idempotencyKey}`) mantem o namespace exato, blindando completamente colisão cross-tenant ou cross-endpoint.
- **Regressão Contratual:** O comportamento permanece alinhado e estrito ao uso da Idempotency-Key. Nenhuma outra assinatura de interface pública ou de webhook payload foi alterada silenciosamente.
- **Typecheck:** O comando `pnpm exec tsc --noEmit` falhou globalmente pelo mesmo problema de conflito de tipagem Drizzle-ORM (`0.45.1` vs `0.35.3`). Como notificado anteriormente, é um débito técnico de infraestrutura da workspace sem relação causal com este ciclo.

### Risco Residual Registrado
- **Condição de Corrida (Race Condition):** A implementação atual usa as operações assíncronas padrão `GET` seguida de `SET` no Redis. Em um cenário de altíssima concorrência real onde o mesmo evento chegue simultaneamente antes da persistência do `SET`, pode ocorrer dupla execução do `processFn`. Como o RED definiu o comportamento sem focar em locks distribuídos robustos (Lua Scripts ou bloqueio atômico `NX`), isso é aceitável na entrega inicial, mas deve ser revisitado num ciclo de estabilização de *Workers/Jobs*.

## REVIEW

### PARECER SECURITY
**APROVADO.** O mecanismo de idempotência atua de forma defensiva para prevenir duplo processamento, sem contornar as assinaturas HMAC nem alterar o pipeline de autorização existente. Seguro e pontual.

### PARECER TENANT ISOLATION
**APROVADO.** O namespace das chaves no cache Redis (`webhook:idempotency:{tenantId}:{endpoint}:{idempotencyKey}`) obriga o particionamento rigoroso e impossibilita que um tenant recupere respostas cacheadas de outro tenant sob nenhuma circunstância.

### PARECER CONTRACT & DB
**APROVADO.** Modificação imperceptível para o consumidor que já trafegava webhooks padrão. O banco de dados primário (PostgreSQL) sequer é tocado nesse processo. Schemas e migrations intactos.
